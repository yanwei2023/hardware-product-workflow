# 公司级产品全生命周期流程平台设计

日期：2026-07-31

状态：已确认设计

适用范围：公司所有产品开发及产品交付项目，以全新产品开发为主

## 1. 目标

将现有硬件开发流程 MVP 扩展为公司级产品全生命周期平台，覆盖：

```text
S0 立项与治理
→ S1 市场调研与产品定义
→ S2 需求与可行性
→ S3 系统总体设计
→ S4 详细设计
→ S5 EVT工程验证
→ S6 DVT设计验证
→ S7 PVT生产验证
→ S8 认证与产品发布
→ S9 交付与运维
→ S10 生命周期管理
```

平台必须支持不同产品类型、技术能力和交付模式，不能把 JW-HFCT 的专用要求固化为所有项目的统一要求。

核心目标：

- 建立公司统一、可版本化的产品开发流程标准。
- 通过项目类型模板和专业能力包适配不同项目。
- 从项目立项到产品退市形成完整文档、证据、决策和审计链。
- Agent 负责起草、检查和提出建议；人类承担审核、批准和最终责任。
- 阶段门只能依据当前有效版本、完整会签、真实证据和风险状态通过。
- 允许项目逐份调整文档等级，但必须经过规定审批并保留审计。

## 2. 总体架构

采用三层可配置架构。

### 2.1 公司通用主干

公司通用主干负责：

- S0-S10 生命周期定义；
- 阶段准入和准出规则；
- 文档编号、版本、基线和归档规则；
- 编制、审核、批准和阶段门权限；
- 风险、问题、CAPA、ECR/ECN 和审计规则。

### 2.2 项目类型模板

首批项目类型：

| 项目类型 | 默认生命周期 |
|---|---|
| 全新产品开发 | 完整 S0-S10 |
| 派生产品/改型升级 | 简化 S0-S1，重点执行 S2-S8 和影响验证 |
| 技术预研/PoC | S0-S3，结论可转入新产品项目 |
| 软件/平台产品 | 保留 S0-S10 语义，以 Alpha/Beta/Release 替代 EVT/DVT/PVT |
| 客户定制产品 | 重点执行需求、设计影响、验证、发布和交付 |
| 产品交付项目 | 从已发布产品基线派生，重点执行 S9 |
| 重大工程变更 | 从现有产品基线派生，执行影响分析、验证和新基线发布 |
| EOL/退市项目 | 执行 S10 退市、备件、服务和客户迁移流程 |

### 2.3 专业能力包

首批专业能力包：

- 电子硬件；
- 嵌入式固件；
- FPGA；
- 算法/AI；
- 结构与工业设计；
- 上位机/平台软件；
- 数据平台；
- 网络与信息安全；
- 认证与计量；
- 可靠性；
- 制造与供应链；
- 现场安装；
- 客户交付；
- 售后与运维。

每个能力包包含默认文档、默认等级、适用性条件、责任角色、所属阶段、门禁规则和依赖关系。

## 3. 文档双轴分类

每份文档同时具有来源类别和门禁等级。

### 3.1 来源类别

| 类别 | 含义 |
|---|---|
| 公司通用 | 所有适用的新产品项目共用 |
| 项目类型 | 由全新产品、派生产品、预研、软件、定制或交付模板带入 |
| 专业能力包 | 由项目选择的硬件、固件、软件、算法、制造等能力带入 |
| 行业/产品专用 | 只属于特定行业或产品，例如 HFCT |

### 3.2 门禁等级

| 等级 | 行为 |
|---|---|
| 必需 | 缺失、版本无效或签核不完整时阻塞阶段门 |
| 条件适用 | 必须完成适用性判断；适用后等同必需，不适用时保留 N/A 依据和批准记录 |
| 普通受控 | 不直接阻塞阶段门，但仍受编号、版本、权限、变更、归档和审计控制 |

`不适用`是适用状态，不是第四种等级。

### 3.3 项目最终等级计算

```text
公司通用默认
+ 项目类型模板
+ 专业能力包
+ 法规/合同要求
+ 经批准的项目级调整
= 项目文档最终等级
```

优先级：

1. 法规、认证和合同明确要求不能被项目级降级。
2. 项目类型和能力包可以将文档加入项目并设为包内必需。
3. 项目经理可以直接升级文档等级。
4. 必需文档降级必须由项目经理申请，质量负责人和阶段门批准人共同批准。
5. 条件文档判定为不适用必须填写依据并由质量负责人批准。
6. 所有调整保存调整前后等级、原因、发起人、批准人、生效阶段和时间。

### 3.4 条件文档状态

```text
待判断
→ 适用：成为项目必需文档
→ 不适用：保存 N/A 理由和批准记录
→ 重新评估：范围、架构、法规或合同变化时触发
```

处于待判断状态的条件文档阻塞对应阶段的门禁准备。

## 4. 项目创建和流程裁剪

```text
选择项目类型
→ 选择专业能力包
→ 回答适用性问卷
→ 系统生成阶段和文档预览
→ 配置项目角色
→ 项目经理确认
→ 质量负责人批准项目流程基线
→ 正式创建项目
```

全新产品开发默认生成完整 S0-S10。项目创建结果必须固化为不可覆盖的项目流程基线。

项目不能直接修改公司文档定义。系统为每个项目生成独立的项目文档需求实例，保存：

- 公司文档定义 ID；
- 文档编号和名称；
- 来源模板或能力包；
- 所属阶段；
- 公司默认等级；
- 项目有效等级；
- 适用状态；
- 调整原因；
- 编制、审核和批准角色；
- 计划完成时间；
- 阶段门影响；
- 当前有效版本；
- 调整历史。

### 4.1 人工升级

普通受控升级为条件适用或必需、条件适用升级为必需时，由项目经理填写原因后直接生效，并通知质量负责人和相关责任人。

### 4.2 人工降级

```text
项目经理申请
→ 填写业务和风险原因
→ 质量负责人批准
→ 阶段门批准人共同批准
→ 生成配置裁剪记录
```

### 4.3 禁止普通降级

以下项目不能通过普通项目调级降级：

- 法律法规明确要求；
- 产品认证明确要求；
- 客户合同或技术协议明确要求；
- 已被重大风险或 CAPA 引用；
- 已作为当前有效基线的一部分；
- 公司质量制度设定为不可裁剪。

### 4.4 自动重新评估

以下事件使相关条件文档恢复为待判断：

- 新增产品型号或形态；
- 新增硬件、软件、算法或通信能力；
- 更换关键技术架构；
- 新增目标市场或认证地区；
- 新增客户合同要求；
- 从研发项目派生交付项目；
- 重大 ECR/ECN 改变原适用性结论。

## 5. 文档、版本和审核

### 5.1 文档主记录

文档主记录保存固定信息：

- 文档编号、名称和类别；
- 所属项目和阶段；
- 编制、审核和批准角色；
- 密级、保存期限和正式存储位置；
- 当前有效版本；
- 上下游关系。

### 5.2 文档版本

每个版本独立保存：

- 版本号和修订说明；
- 文件或结构化内容；
- 创建人和创建时间；
- 输入文档及其版本；
- 评审、批准和签名记录；
- 证据附件；
- 所属基线；
- ECR/ECN 关联。

审核必须绑定具体 `documentVersionId`，不能只绑定工作包或文档主记录。

### 5.3 版本状态

```text
计划中
→ 草稿
→ 编制人自检
→ 专业审核中
→ 交叉评审中
→ 待批准
→ 已批准
→ 已基线/已发布
→ 被替代
→ 已作废
→ 已归档
```

审核要求修改时创建新修订版本。已基线版本不能原地修改。

### 5.4 版本号

| 版本 | 含义 |
|---|---|
| V0.x | 草稿、评审稿和返工稿 |
| V1.0 | 首次正式批准基线 |
| V1.x | 不改变主要范围的受控修订 |
| V2.0 及以上 | 范围、架构、产品代际或重大技术路线变化 |

系统提供建议版本号，配置管理员确认正式版本号。

### 5.5 职责分离

1. 编制人不能同时作为唯一审核人。
2. 必审角色集合中的所有角色必须对同一版本完成审核。
3. 批准人必须看到全部审核意见和关闭证据。
4. 安全、质量、认证和可靠性文件必须有质量或独立评审。
5. 代理审批必须记录授权来源和有效期。
6. 同一人员承担多个角色时提示职责冲突；关键文件禁止单人完成全部签核。

审核决定：

- 同意；
- 有条件同意；
- 要求修改；
- 拒绝；
- 要求补充证据；
- 升级处理。

## 6. 基线、追溯和影响分析

### 6.1 阶段基线

阶段门批准时生成不可修改的阶段基线，包含：

- 阶段门决策；
- 所有门禁文档的精确版本；
- 审核和批准记录；
- 需求追溯快照；
- 风险和豁免；
- 遗留条件；
- 原始测试和证据引用；
- 审计记录。

后续变更通过 ECR/ECN 创建新版本和新基线。旧版本保留并标记被替代。

### 6.2 追溯关系

系统支持以下有类型关系：

- 来源于；
- 分解为；
- 实现；
- 验证；
- 证据；
- 影响；
- 替代；
- 包含于；
- 派生。

P0/P1 需求必须形成：

```text
需求
→ 设计
→ 测试用例
→ 测试结果
→ 缺陷/豁免
→ 发布版本
```

### 6.3 版本变化影响

```text
上游版本变化
→ 查找下游关系
→ 标记待影响评估
→ 负责人判断无影响/需要修订/需要回归
→ 质量负责人确认
```

待影响评估或需要修订的门禁文档不能用于阶段门通过。

## 7. 阶段门

阶段门就绪必须满足：

1. 必需文档存在。
2. 条件文档完成适用性判断。
3. 适用文档具有当前有效版本。
4. 必审角色对同一版本完成审核。
5. 批准人批准该版本。
6. 版本未被替代、作废或标记待影响评估。
7. 必需证据存在且可以访问。
8. P0/P1 需求追溯链完整。
9. 高风险和严重风险已关闭或被授权人正式接受。
10. 严重缺陷、法规、安全和认证问题已关闭。
11. Agent 高风险发现和质量审核问题已处理。
12. 不存在逾期的阶段门放行条件。

阶段门结论：

- 通过；
- 有条件通过；
- 不通过/返工。

有条件通过必须记录条件或豁免编号、风险等级、责任人、期限、验证方法、关闭证据、批准人和是否允许带入下一阶段。

以下情况禁止有条件放行：

- 法规或认证硬性要求未满足；
- 产品安全问题未关闭；
- 严重风险未处置；
- 必需文档缺失；
- 必需角色未签核；
- 当前有效版本无法确认；
- P0 需求没有验证方案。

## 10. 权限

采用组织角色、项目角色和对象权限三层模型。

| 角色 | 核心权限 |
|---|---|
| 系统管理员 | 用户、组织和系统配置，不默认拥有工程批准权 |
| 公司流程负责人 | 维护 S0-S10 和项目类型模板 |
| 公司质量负责人 | 发布质量规则、批准流程例外 |
| 配置管理员 | 文档编号、版本、基线、发布和归档 |
| 项目发起人 | 批准立项、预算、重大变更和发布 |
| 项目经理 | 裁剪流程、分配责任、发起调级和组织阶段门 |
| 专业负责人 | 编制、审核专业文档和关闭问题 |
| 测试负责人 | 测试策略、证据和验证结论 |
| 质量负责人 | 独立审核、风险、CAPA 和阶段门质量意见 |
| 阶段门批准人 | 阶段放行决策 |
| 交付负责人 | 交付项目、安装、验收和现场闭环 |
| 观察者/审计员 | 只读查看和导出 |

系统管理员不会自动获得业务批准权。

## 11. 事务和异常

以下操作必须原子执行：

- 项目创建与流程基线生成；
- 文档批准与版本状态变化；
- 阶段门批准与基线固化；
- ECR/ECN 生效与版本替换；
- 项目调级审批；
- 产品项目派生交付项目。

任一子步骤失败时全部回滚。

其他约束：

- 使用乐观锁防止并发覆盖；
- 数据库失败时清理孤立上传文件；
- 评审期间内容变化使已有签核失效；
- 模板或能力包冲突时禁止创建项目；
- 能力包缺少依赖时要求补选；
- 审核人失去授权时重新分配未完成审批；
- 正式文档和审计记录不得物理删除；
- 被拒绝和失败的操作同样记录审计事件。

## 12. 现有 MVP 迁移

现有模板保留为：

```text
hardware_mvp_pilot_v0_1
```

迁移规则：

1. 历史项目不自动扩展为 S0-S10。
2. 历史项目保持可读和可导出。
3. 新项目默认使用公司全生命周期模板。
4. 提供迁移向导映射阶段、工作包和文档。
5. 旧 Artifact 转换为 DocumentVersion。
6. 旧 Review 绑定可确定的版本；无法确定时标记历史关系待确认。
7. 迁移先预览和校验，再由项目经理和质量负责人确认。
8. 迁移前生成完整快照和回滚点。

## 13. 验收

完整业务场景：

1. 全新硬件产品；
2. 软件/平台产品；
3. 从产品基线派生的客户交付项目；
4. 从发布基线发起的重大工程变更。

必须验证：

- 必需文档缺失时不能通过阶段门；
- 条件文档未判断时不能进入阶段门评审；
- 不同版本的审核和文档不能组合通过；
- 缺少任一必审角色签核时不能批准；
- 普通用户不能降级必需文档；
- 法规和合同文档不能被项目级降级；
- 上游变化未完成影响评估时不能放行；
- 严重安全或法规问题不能有条件通过；
- 失败事务不会留下半完成状态；
- 历史版本、审计和基线不能被删除或覆盖。

## 14. JW-HFCT 文档清单拆分

以下分级将 JW-HFCT 的 100 份文档转为公司通用定义、项目类型规则、专业能力包和 HFCT 产品包。`包内必需`表示只有相应模板或能力包启用时才进入项目并阻塞门禁。

### 14.1 S0-S4
